## Первые задачи разработки

В таком порядке, небольшими проверяемыми PR:

1. **REL-01 — Сборка и консолидация.** Инвентаризировать незакоммиченные изменения в обоих деревьях; зафиксировать безопасные snapshots без секретов. Разобрать PR, не сливая все дубли. Убрать побочные push из quality, исправить ESLint и sitemap. CI: install → typecheck → lint → i18n → build. Ботам не разрешать прямые изменения main.
2. **REL-02 — Согласованная БД.** Read-only экспорт схемы/политик/триггеров/GRANT, сравнение с миграциями. Исправить jobs.title, notifications link/payload/старые triggers, рекурсию profiles. Не удалять production таблицы и историю миграций как «мусор». Schema reset только в одноразовом staging.
3. **SEC-01 — Права аккаунта и приватность.** Публичная проекция мастера; приватные phone/chat_id/геоточка; пользовательские поля отдельно от admin/credits/verified/rating. Тестовые actors: guest, A, B, worker, blocked, admin. Закрыть также grants старых RPC.
4. **FLOW-01 — Отклик с учётом кредитов.** Одна транзакция, один ledger entry; actor из сессии; valid active job, не свой заказ, не истёкший, не blocked; уникальность и повтор безопасны.
5. **FLOW-02 — Выбор, отмена, завершение.** Одна машина состояний, победитель из bid, locks/expected state; рейтинг только по завершённым работам. Прямой UPDATE не позволяет обойти правила.
6. **AUTH-01 / TG-01 — Сессии и привязка.** Ошибка чтения профиля не означает «новый пользователь»; refresh/logout/relogin тесты; одноразовые Telegram токены с TTL и secret header.

Первые четыре пункта важнее новых карточек, анимаций, дополнительных городов и платной рекламы.

## Предлагаемый объём пилота

Рабочая рекомендация до согласования: Бельцы, 2–3 категории с доступными мастерами, RU/RO, бесплатный пилот с прозрачным техническим лимитом откликов. Один пользователь может и размещать заявки, и выполнять работы; admin — отдельная привилегия, не переключатель профиля.

Точку пользователь отмечает вручную или получает через GPS с подтверждением. Публично показывать приблизительный район, точную точку раскрывать только сторонам выбранной работы. Не отправлять точные координаты в analytics. Если будет выбрана вся Молдова, сначала согласовать city IDs, локализацию, coverage и операционные возможности; не расширять обещания просто добавлением городов в массив.

Платный запуск — отдельный gate: реальная компания/получатель, подтверждённые реквизиты, единые цены, понятные возвраты, журнал начислений и сверка платежей. Переписка с поддержкой и кнопка «+10» не являются достаточным платёжным процессом. Наличие платежей не обязательное условие бесплатного пилота.

## Организация QA и Jira

Epics: REL Foundation; SEC Access & Privacy; FLOW Marketplace; AUTH & Notifications; UX RU/RO; OPS Trust & Launch. Каждое Rxx из ревью — отдельная bug/story с приоритетом; не объединять всё в задачу «починить сайт».

Карточка задачи: проблема/триггер → ожидаемое поведение → source file/line → риск → acceptance criteria → test cases → staging evidence → PR → migration dependency. Для бага нужны шаги воспроизведения и actor. Секреты и персональные данные в Jira не помещать.

Статусы: Backlog → Ready → In progress → Review → QA staging → Done. WIP одного founder: максимум одна реализация и одна проверка. Done означает проверку поведения, а не только commit или зелёный preview.

| Набор | Что проверяет | Где/когда |
|---|---|---|
| Unit | Валидация сумм/UUID/category/locale, safeNext, нормализация местоположения, credit arithmetic | Каждый PR |
| DB integration / pgTAP либо API harness | Матрица RLS/grants, RPC actor, privileged columns, trigger schema, ledger, rollback, concurrency | Изолированная Supabase/Postgres среда на PR |
| Playwright | Регистрация/профиль → заявка → второй аккаунт bid → выбор → контакты → done/review; отказ сети и повтор | Preview + staging DB; без платных SMS в обычном CI |
| Ручной smoke | Реальный OTP на согласованных тестовых номерах, iOS/Android GPS/cookies, экранная клавиатура, фото HEIC | Перед пилотом и изменениями auth/providers |
| Release smoke | RU/RO public pages, 404/500, logout, роли, webhook health, alerts, backup restore | На release candidate, затем безопасная проверка production |

Тесты на деньги, конкурирующие запросы и авторизацию обязательны. Процент покрытия сам по себе не является критерием запуска.

## Пилот, метрики и первые 90 дней

Это предлагаемые цели, не фактические показатели сервиса:

- До открытия: 10–15 согласившихся мастеров в выбранных категориях, работающий канал поддержки, инструкции мастерам; никаких вымышленных рейтингов/счётчиков/значков.
- Пилот 7–14 дней: 10–20 реальных заявок, сопровождение выбора и последующего завершения; при низкой ликвидности продлить пилот, а не запускать рекламу по всей стране.
- День 1–30 после релиза: локальные группы и рекомендации, ручное подключение предложения, еженедельное интервью с клиентами; расход на рекламу только после утверждения бюджета.
- День 31–60: улучшать категории с реальным спросом, время первого релевантного отклика и долю выбора. Проверить желание платить, не считать начисленные кредиты выручкой.
- День 61–90: включать монетизацию и следующий город лишь при стабильных завершениях, работающей поддержке и понятной экономике привлечения.

События: auth_verified, profile_completed, job_created, bid_created, worker_selected, job_completed, review_created, report_submitted. Для бизнес-событий — server-side факт/idempotency, без телефонов/текста заявки/координат в analytics.

| Метрика | Определение | Предложенный ориентир пилота |
|---|---|---|
| Покрытие заявок | Заявки с ≥1 допустимым откликом за 24 ч / подходящие заявки старше 24 ч | ≥70% |
| Liquidity | Заявки с выбранным мастером / реальные подходящие заявки когорты | ≥30%, обязательно показывать n |
| Время первого отклика | Median и p90 от публикации до первого релевантного отклика | Измерить; не обещать «15 минут» до данных |
| Завершение | Done / выбранные работы, срок которых уже наступил | Тренд + причины незавершения |
| Надёжность | Доля успешных критичных операций, ошибки/дубли/потерянные кредиты | 0 потерь/чужих доступов; все P0 закрыты |
| Экономика | Реальная выручка минус SMS, инфраструктура, платежные комиссии, поддержка и привлечение | Считать на фактических затратах; платежи могут быть отключены |

Ghost clients: напоминание, явная отмена, срок заявки, лимит незавершённых публикаций, жалоба/апелляция. Fake workers: прозрачные уровни проверки и отзывы только после заказа. Off-platform leakage: удерживать полезностью статуса, поддержки и отзыва; не обещать запрет контактов, если они публичны через API.

## Решения владельца до публичного запуска

| Решение | Текущий статус | Рекомендация |
|---|---|---|
| Бельцы или вся Молдова; обязательность pin | История и реализация расходятся | Узкий пилот, подтвердить scope |
| Коммерческое имя/домен/контакты | В коде несколько доменов и неподтверждённых адресов | Один действительный origin и проверенные каналы; @kentukaa уже указан пользователем |
| Смысл «Проверен», нужны ли ID-документы | Реальный процесс не определён | Начать с минимальных данных; паспорт только при обоснованной необходимости и процедуре хранения |
| Бесплатный пилот или платные кредиты | Два несогласованных прайс-листа | Бесплатный пилот, отдельное утверждение оплаты |
| Юридические тексты/регион/retention | Черновики с неподтверждёнными обещаниями | Сверить факты и проверить с местным специалистом до публикации |
| Кто отвечает на жалобы и инциденты | Роль оператора не зафиксирована | Founder с реальным графиком и каналом эскалации |

Эти решения не блокируют подготовку кода, тестов и staging. Публикацию условий, запуск оплаты и production-миграции согласовывать на конкретном проверенном результате.

## Ритм работы и журнал решений

Ежедневно: что проверено, текущий blocker, следующий шаг, ссылка на evidence. Еженедельно: состояние P0/P1, готовность gates, затраты/метрики, решения владельца. Не называть процент готовности по количеству страниц.

Decision log: дата → вопрос → варианты → выбранное решение → кто утвердил → влияние → ссылка на PR/тест. На дату этого плана новая география, цены, юридические обещания и публичный релиз не утверждены.

После релиза: ежедневный просмотр критичных ошибок и очереди поддержки первую неделю; проверка транзакций и уведомлений; rollback frontend по deployment ID, DB — отдельным проверенным recovery/forward-fix планом. Откат сайта не откатывает миграции и данные.
