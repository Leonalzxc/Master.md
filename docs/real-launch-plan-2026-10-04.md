# Реальный запуск MASTER Moldova

Владелец поручил подготовку и исполнение 04.10.2026. Рабочая версия:
`codex/stabilize-bids`; объединение с `main` сохранено в `132a201`.
Все завершённые этапы сохраняются отдельными коммитами.

## Цель и порядок

Релиз готов, когда два разных пользователя проходят путь:
SMS → анкета → заявка с местом → отклик → выбор мастера → закрытые контакты
→ завершение → один отзыв. Ошибки сети и повторы не портят данные.

| Этап | Действия | Доказательство готовности | Состояние 04.10 |
|---|---|---|---|
| 1. Код и проверки | Свести main, исправить сборку, CI без автопушей | Чистая установка, lint/typecheck/build, PostgreSQL tests | Выполнено локально; CI должен пройти на PR |
| 2. Отклики и баланс | Одна транзакция; безопасный повтор; закрыть прямой INSERT и изменение кредитов | Ошибки и rollback; реальные параллельные соединения | 20 тестов и сборка прошли; concurrency в работе |
| 3. Заказ и отзыв | Атомарные выбор/отмена/завершение; исполнитель из отклика; ограничения REST | Гонки выбора/отмены; чужие аккаунты; rating/notifications один раз | В работе |
| 4. Вход и Telegram | Безопасный next, одноразовые ссылки с TTL, secret header, ошибки доставки | Чужой UUID не привязывается; повтор webhook; refresh/logout | В работе |
| 5. Приватность и UI | Контакты/координаты только участникам; RU/RO; мобильные формы; реальные сообщения ошибок | Негативные REST/RLS tests; браузерный сценарий двух пользователей | Частично; профильная миграция локально готова |
| 6. Подготовка пилота | Согласовать город/оплату; реальные сведения оператора; поддержка; backup/restore | Никаких выдуманных реквизитов; подтверждённый restore; контакт поддержки | Ожидаются решения/доступ |
| 7. Staging и выкладка | Применить миграции к копии схемы; PR/CI; связанная выкладка БД и кода | Migration ID + deployment SHA; smoke после выкладки | Ожидается SQL-доступ и вход Vercel |
| 8. Пилот | Первые реальные мастера/заказчики; сопровождение; ежедневные ошибки/воронка | Завершённые реальные заказы и решение о расширении | После технического Go |

Не запускаем рекламу до проверки основного пути. Дата публикации определяется
прохождением условий, а не обещанием календарного дня.

## Выполнение и решения

- GitHub: доступ подтверждён. 30 старых PR направлены в устаревшую рабочую
  ветку; их массовое слияние не требуется. Новая release-ветка должна идти в main.
- Vercel CLI: повторный вход требуется. Existing production:
  `https://master-md.vercel.app`. `.md` домен не считается настроенным.
- Локально есть только публичные Supabase URL/key. Для DDL нужен SQL Editor,
  подключённый management API или разрешённое DB-подключение; публичного
  REST key недостаточно. Секреты не помещать в чат/репозиторий.
- Предлагаемый первый выпуск — бесплатный пилот в Бельцах, RU/RO.
  Решение владельца о географии/оплате запрошено; ожидание не останавливает
  исправления общего ядра. Цены и сведения юридического оператора не выдумываются.
- Без SQL-доступа нельзя объявить production защищённым. Без подтверждённого
  входа Vercel нельзя утверждать, что проверенный SHA опубликован.

## Процедура выпуска

1. Сохранить штатный backup БД и экспорт GRANT/RLS/functions/triggers.
2. В изолированной staging-копии применить обновления в документированном порядке,
   проверить старые дополнительные triggers и несовместимые схемы notifications.
3. Проверить release build и пользователей A/B на staging, включая отказы сети.
4. Опубликовать PR в main; проверить CI и связать SHA с Vercel deployment.
5. В согласованном окне применить SQL и тот же код. Старые действия прямого REST
   после ограничений перестанут работать: это связанная выкладка.
6. Выполнить smoke: гостевой каталог, запрет приватных полей, оба аккаунта,
   один отклик/кредит, выбор, отзыв, роль, logout/refresh, уведомления.
7. Зафиксировать SHA, migration IDs и результат. При сбое сохранить ограничения
   данных и исправить код; frontend rollback не отменяет SQL.

## После публикации

Ежедневно первую неделю: критичные ошибки, недоставленные сообщения, жалобы,
новые заявки/отклики/завершения. Еженедельно: решения, KPI пилота и следующий
набор исправлений. Реальная проверка спроса и работа с юридическим оператором
требуют участия владельца; тестовые данные не заменяют эти результаты.
