## Цель и порядок

Релиз готов, когда два разных пользователя проходят путь:
SMS → анкета → заявка с местом → отклик → выбор мастера → закрытые контакты
→ завершение → один отзыв. Ошибки сети и повторы не портят данные.

## Процедура выпуска

1. Сохранить штатный backup БД и экспорт GRANT/RLS/functions/triggers.
2. В изолированной staging-копии применить обновления в документированном порядке,
   проверить старые дополнительные triggers и несовместимые схемы notifications.
3. Проверить release build и пользователей A/B на staging, включая отказы сети.
4. Опубликовать PR в main; проверить CI и связать SHA с Vercel deployment.
5. В согласованном окне применить SQL и тот же код. Старые действия прямого REST
   после ограничений перестанут работать: это связанная выкладка.
6. Выполнить smoke: гостевой каталог, запрет приватных полей, оба аккаунта,
   один бесплатный отклик/повтор, выбор, отзыв, роль, logout/refresh, уведомления.
7. Зафиксировать SHA, migration IDs и результат. При сбое сохранить ограничения
   данных и исправить код; frontend rollback не отменяет SQL.

## После публикации

Ежедневно первую неделю: критичные ошибки, недоставленные сообщения, жалобы,
новые заявки/отклики/завершения. Еженедельно: решения, KPI пилота и следующий
набор исправлений. Реальная проверка спроса и работа с юридическим оператором
требуют участия владельца; тестовые данные не заменяют эти результаты.

## Публикация без дублей

`publish_pilot_job` связывает случайный UUID формы с владельцем, созданной
заявкой и отпечатком данных в одной транзакции. Повтор после потерянного ответа
возвращает тот же ID без нового уведомления и расходования суточного лимита.
Изменённый повтор возвращает конфликт и ссылку на ранее созданную заявку;
старое содержимое не перезаписывается. Ключ живёт в текущей форме, не в
localStorage: закрытие страницы не обещает восстановление черновика.

Прямой authenticated INSERT jobs закрыт, включая прежние column grants.
RPC принимает только данные формы; owner/status/id/created_at нельзя передать.
Дата создания и 7/30-дневный срок устанавливаются базой. Бюджет ограничен
0–1 000 000 000 MDL, максимум двумя десятичными знаками; пустое описание,
неверные типы/категория/точка и чужие фото отклоняются до фиксации.

Переход из шага фото и сохранение профиля блокируются до конца загрузки,
включая повторный клик до перерисовки. Сетевая ошибка снимает блокировку;
полученные снимки остаются в форме. После успешной публикации повторная
отправка блокируется до перехода на страницу заявки.

Последняя локальная проверка: 80 tests, lint, 133 RU/RO keys, client boundaries,
production build и typecheck PASS; 14 PostgreSQL tests отдельных соединений
PASS. Среди новых гонок — один UUID/одна заявка и конкуренция за пятую заявку.
SQL пакет с девятью миграциями проверен на повтор и полный rollback.
Production не изменён; password authentication 28P01 остаётся препятствием
для backup/restore. Сброс лимита Codex не означает сброс пароля PostgreSQL.
