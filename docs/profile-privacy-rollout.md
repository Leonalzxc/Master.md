# Исправление создания заявки и доступа к профилям

## Что изменено

- createJob больше не вставляет `jobs.title`: живой схеме достаточно description. Убрано и требование title из типа JobInsert.
- Публичные запросы профилей используют явный список полей. Телефон и Telegram chat ID не нужны каталогу, SEO и именам авторов отзывов.
- Миграция `web/supabase/migrations/202609230001_profile_contact_privacy.sql` снимает старые table/column grants с profiles и возвращает доступ только к разрешённым полям. Данные не удаляются и не переносятся.
- Кабинет получает собственные данные через get_my_profile(), без передаваемого userId. Ошибка чтения больше не вызывает upsert со сбросом роли.
- get_job_client_contact(jobId) раскрывает только name/phone заказчика выбранному исполнителю: нужен in_progress, совпадение selected_worker_id, выбранный bid и отсутствие блокировки у обеих сторон.
- INSERT профиля ограничен своим auth.uid и подтверждённым телефоном. Роли client/worker можно менять; admin нельзя назначить/снять через пользовательскую форму. Изменение phone/chat ID/блокировки прямым клиентским UPDATE запрещено.
- Серверные уведомления получают Telegram ID через service-role клиент после проверки основного действия. Админские изменения используют такой клиент только после проверки текущего пользователя, роли и блокировки.
- Sitemap использует обычный клиент: public build больше не требует service-role ключа.

## Область исправления

Это исправление доступа к `profiles.phone` / `profiles.telegram_chat_id` и создания заявки, а не завершение всего security backlog. В частности, отдельными задачами остаются одноразовая Telegram-привязка, атомарный lifecycle/кредиты, системные поля profiles_worker, приватность его viber/telegram/whatsapp, обработка точных координат и фото. Существующие роли admin в БД нужно проверить на легитимность: миграция предотвращает новые самоназначения, но не угадывает, кто был назначен законно раньше.

## Проверка перед применением

Изолированные PostgreSQL-тесты через PGlite, без подключения к production:

```sh
npm install --prefix /tmp/master-md-pg-privacy-tests --no-package-lock --ignore-scripts --no-audit --no-fund @electric-sql/pglite@0.5.8
cd web
PGLITE_MODULE_PATH=/tmp/master-md-pg-privacy-tests/node_modules/@electric-sql/pglite/dist/index.js node --test scripts/test-profile-privacy.mjs
npm run typecheck
npm run build
```

PGlite установлен только во временную директорию, package.json/lockfile приложения не менялись. Нужны локальные зависимости web, включая TypeScript. Тесты используют синтетические номера и аккаунты, не отправляют OTP/Telegram и не загружают .env.

Проверяются: анонимные прямые/вложенные/фильтрующие SELECT приватных полей, доступ к своей анкете, доступ победителя и отказ другим участникам, блокировка/завершение, смена ролей, запрет admin, подтверждённый телефон, сервисные уведомления, повторный запуск миграции и реальный INSERT из createJob против схемы без title.

Результат локального прогона: **10/10 тестов**, `npm run typecheck`, `npm run build`, i18n key sync (133/133), проверка Supabase client/server boundary и `git diff --check` прошли. Full ESLint не заявляется успешным: его конфигурация была сломана ещё на этапе ревью и в этой задаче не менялась. При typecheck обнаружены три старых дубликата сгенерированных `.next/types/* 2.ts`; они перенесены во временную резервную директорию, исходники не удалялись.

## Порядок выкладки

1. Согласовать изменения этой рабочей ветки с актуальным main. Не выкатывать весь накопленный локальный diff вслепую: в нём есть более ранние несвязанные изменения.
2. На staging с существующей схемой применить миграцию целиком. Требуются таблицы profiles/jobs/bids, колонка telegram_chat_id и ранее исправленные рекурсивные RLS. Сверить GRANT/политики/публичные views на live: вне этого репозитория могли быть дополнительные пути доступа.
3. Проверить новый код на этом staging: OTP/профиль/сохранение, каталог/отзывы, выбранный исполнитель, админка и Telegram. Service-role ключ нужен только серверным webhook/уведомлениям/админке и не должен иметь NEXT_PUBLIC префикса.
4. Подготовить проверенный release build. Применить SQL через Supabase Dashboard → SQL Editor на правильном проекте и развернуть **тот же** проверенный код в согласованном окне обслуживания. До применения RPC новая версия кабинета выдаст ошибку; после ограничения grants старая версия с SELECT * перестанет читать profiles. Это связанная выкладка БД + приложения.
5. После выкладки проверить из отдельного гостевого окна: каталог работает, REST select=phone и select=telegram_chat_id отклоняются. Под своим аккаунтом профиль показывает собственный номер, второй пользователь не читает его напрямую. Контакт заказчика доступен только выбранному мастеру.
6. Записать migration ID, deployment SHA, время и результаты smoke. Production до этих шагов не считается исправленным.

На момент подготовки локально нет доступа к выполнению DDL: отсутствует DATABASE_URL/подключённый Supabase management API. SQL не применялся к живой базе. Даже service-role API key сам по себе не даёт универсального SQL/DDL endpoint.

Откат: не восстанавливать публичный SELECT всех столбцов ради старого интерфейса. При проблеме приостановить проблемный экран и исправить совместимый код, сохраняя ограничение приватных полей. До миграции сохранить metadata/grants и штатную резервную копию; восстановление БД — отдельная операция, откат Vercel его не делает.
